# 当前实现（Demo演进）与 docs 架构设计（目标态）功能点对齐分析与修改指导

## 1. 背景与分析口径

你的说明很关键：

- **当前实现**：是从 demo 持续演进出来的“可运行系统”，强调可用性与落地速度。
- **docs 设计**：是后续从架构视角抽象出的“目标态方案”，强调扩展性、规范性和平台化。

因此，这不是简单的“谁对谁错”，而是**两条路径在不同阶段的合理产物**。本分析不再以技术栈差异为中心，而是聚焦“智能问题定位”的核心功能闭环：

> 输入问题 → 诊断编排 → 证据采集 → 假设/结论 → 行动建议 → 风险控制 → 复盘沉淀。

---

## 2. 两套设计的功能点对照（围绕最终目标）

## 2.1 当前实现（Demo演进）已具备的优势功能

1. **可运行的诊断主链路**
   - 已具备诊断启动/暂停/恢复/停止、审批确认、状态推进等控制能力。
2. **多 Agent 协作执行能力**
   - 已有协调、日志、代码、知识、指标等角色化执行组件。
3. **实时交互链路**
   - WebSocket 支持会话级事件推送和控制指令回传。
4. **可追踪状态与事件存储**
   - 已有 session 快照 + 事件 + 执行记录，支持回放与审计基础。
5. **工程化基础较完整**
   - 前后端分层、测试、迁移脚本、运行监控等已具备基础能力。

> 结论：当前实现的核心价值是“先跑通问题定位业务”，在执行链路上已经接近可生产化。

## 2.2 docs 架构设计（目标态）强调的关键功能

1. **Skill 平台化**
   - 通过可插拔 Skill 做领域解耦，降低新增场景成本。
2. **工具体系标准化**
   - 工具注册、权限、执行约束、审计模型更完整。
3. **知识检索体系化（RAG）**
   - 对历史案例、文档、知识数据进行统一检索与增强。
4. **统一协议与模型规范**
   - API/WS/数据模型趋于统一，便于跨端协同和自动生成文档。
5. **面向规模化协作的架构治理**
   - 关注可扩展、可维护、可治理，而非单一 demo 闭环。

> 结论：docs 的价值是“把问题定位系统从能跑提升到可扩展的平台”。

## 2.3 关键互补关系（不是替代关系）

- 当前实现擅长：**业务闭环落地**（能诊断、能交互、能执行、能回放）。
- docs 方案擅长：**平台化演进**（可插拔、可复用、可治理、可扩域）。

最终目标应是：

> 以“当前实现”作为生产骨架，按 docs 的功能抽象逐步内聚到统一能力平台。

---

## 3. 面向“智能问题定位”目标的能力地图（建议统一口径）

建议将全项目收敛到以下 6 个一级能力域，并据此改造代码与文档：

1. **诊断编排能力**：任务拆解、Agent 调度、模式路由、过程控制。
2. **证据采集能力**：日志/指标/代码/知识等多源数据采集与标准化。
3. **推理决策能力**：假设生成、证据打分、根因收敛、置信度管理。
4. **执行治理能力**：风险分级、审批确认、安全边界、幂等保障。
5. **交互呈现能力**：实时状态、行动建议、时间线、回放与复盘。
6. **知识沉淀能力**：案例归档、知识结构化、检索增强、反馈闭环。

每个后续需求都归类到这 6 类，避免“技术栈驱动开发”。

---

## 4. 修改指导方案（可执行版本）

## 阶段 A：功能基线统一（1~2 周）

目标：先统一“我们现在有哪些功能、最终要哪些功能”。

1. 建立《功能基线清单》
   - 按上述 6 大能力域，分别列 `已实现 / 部分实现 / 待实现`。
2. 文档改版为“双视图”
   - 每份核心文档都拆成：
     - `As-Is（当前可运行）`
     - `To-Be（目标架构）`
3. 定义统一术语
   - 会话、任务、诊断阶段、证据、假设、结论、行动、确认等概念统一。

交付物：
- `docs/capability-baseline.md`
- 改版后的 architecture/api/websocket/database 文档（增加 as-is/to-be 分栏）

## 阶段 B：核心闭环增强（2~4 周）

目标：围绕“定位效率与准确性”补齐关键功能，而不是先大改框架。

1. 统一证据模型
   - 将日志/指标/代码/知识结果映射为统一 Evidence Schema（含来源、时间、置信度、可追溯 ID）。
2. 统一诊断输出模型
   - 标准化 Root Cause / Evidence / Confidence / Action Plan / Risk / Rollback。
3. 强化诊断过程可观测性
   - 给关键节点补埋点：任务排队、Agent 耗时、证据命中率、结论变更轨迹。
4. 强化人机协同节点
   - 对高风险动作保留强制确认；低风险动作支持策略化自动执行。

交付物：
- `docs/diagnosis-output-spec.md`
- 协议字段补齐与前后端展示对齐

## 阶段 C：平台化抽象落地（4~8 周）

目标：将 docs 的架构优势“增量接入”当前系统。

1. Skill 最小可用化
   - 先落地 Skill 元数据 + 生命周期 + 执行审计，不一次性做复杂依赖图。
2. 工具体系治理化
   - 对工具能力增加权限级别、超时、资源限额、失败分级策略。
3. 知识闭环产品化
   - 将诊断结论自动沉淀为案例，支持“相似问题召回 → 复用行动建议”。
4. 兼容性演进策略
   - API/WS 增加版本字段与兼容窗口，避免一次性破坏联调生态。

交付物：
- `docs/skill-runtime-minimum-spec.md`
- `docs/tool-governance-spec.md`
- `docs/knowledge-loop-spec.md`

## 5. 功能优先级建议（按“最终目标收益”排序）

### P0（必须先做）

1. 诊断输入/输出模型统一（直接影响定位质量与可复盘性）。
2. 证据模型统一（直接影响多 Agent 协作有效性）。
3. 风险控制与确认策略清晰化（直接影响线上安全）。
4. 文档 as-is/to-be 双视图（直接影响协作效率和需求对齐）。

### P1（第二优先）

1. Skill 最小能力接入（提升扩展效率）。
2. 案例沉淀与相似问题召回（提升诊断速度）。
3. 协议版本治理与契约测试（提升升级稳定性）。

### P2（持续建设）

1. 更细粒度的工具治理与成本优化。
2. 更完整的领域模板（K8s、数据库、中间件等）。
3. 组织级指标体系（MTTR、一次定位成功率、自动化处置率）。

---

## 6. 实施原则（避免再次“设计与实现脱节”）

1. **功能优先于技术栈争论**：先看是否提升定位效率与准确率。
2. **增量演进而非重写**：在当前可运行链路上抽象平台能力。
3. **契约先行**：API/WS/数据结构统一由 contract 驱动。
4. **文档随代码发布**：每次功能变更必须同步 as-is 与 to-be 差异。
5. **可量化验收**：每个阶段至少绑定 2~3 个可观测指标（如诊断时长、误判率、审批等待时长）。

---

## 7. 一句话落地建议

把当前项目当作“诊断执行内核”，把 docs 设计当作“平台化路线图”；以“功能闭环收益”做唯一排序标准，分阶段把 Skill、工具治理和知识闭环逐步接入，而不是一次性架构重构。
